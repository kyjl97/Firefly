## 2026-08-23 - larkdoc（ChrisZou/larkdoc）源码级适配：去掉 --json、补 --as user、在 Go 子进程内过滤 Hermes 环境变量

### 场景

装好 [chriszou/larkdoc](https://github.com/chriszou/larkdoc) v0.1.1 后第一次跑 `larkdoc`，期望把有权限的飞书文档全量同步到本地 `~/.larkdoc/`，再做交互式模糊搜索。

### 错误 / 弯路

1. `larkdoc sync --full` 第一页就报 `lark-cli 调用失败: Error: unknown flag: --json`。
2. 删掉源码里的 `--json` 后再编译，跑出 `resolved identity "bot" (via auto-detect or default-as) is not supported, this command only supports: user`，必须显式 `--as user`。
3. 加上 `--as user` 后变成 `hermes context detected but lark-cli is not bound to it`——Codex 桌面给外部命令注入了 Hermes 网关的检测变量（`HERMES_HOME` / `HERMES_QUIET` / `HERMES_EXEC_ASK` / `HERMES_GATEWAY_TOKEN` / `HERMES_SESSION_KEY`），lark-cli 把它当成 Hermes CLI 上下文。
4. 即便把源码层三处问题都补上，最终还会卡在 `need_user_authorization ... current command requires scope(s): search:docs:read`，因为 `lark-cli` 本机 user 配置（飞书 app `cli_a945002535781cb0`，用户「得救之道 kyjl97.github.io」）还没授予 search 权限。

### 根因分析

1. larkdoc v0.1.1 是 Go 写的、依赖本机 `lark-cli`，假设的是某个早期版本 lark-cli（支持 `--json` flag）。当前 npm 全局装的 `@larksuite/cli` 用 `--format` 控制输出，且默认就是 json；多余的 `--json` 会被当作 unknown flag 拒绝。
2. `lark-cli drive +search` 和 `docs +fetch` 只允许 `user` 身份（Risk: read），larkdoc 没传 `--as user`，lark-cli 默认走 `bot` 就直接报错。
3. `lark-cli` 启动时会探测 Hermes 网关的 5 个检测变量（`HERMES_HOME` / `HERMES_QUIET` / `HERMES_EXEC_ASK` / `HERMES_GATEWAY_TOKEN` / `HERMES_SESSION_KEY`，判定逻辑在 `internal/core/workspace.go:113-117`）。只要命中任意一个就判定为 Hermes 调用上下文。如果在，但 `lark-cli` 又没绑定过这个 Hermes，就会报「context detected but not bound」。这条根因和 2026-07-30 那条记录完全同源，但 larkdoc 是编译后的 Go exe，没法像 PowerShell 那样 `Remove-Item Env:HERMES_HOME`，必须在源码里清。
4. larkdoc 同步元数据走 `drive +search` 全量翻页，必须先拿到 `search:docs:read`；最小权限原则下，只要补这一个 scope，不要顺手申请全部权限。

### 解决方案 / 正确做法

1. **从源码重新编译 larkdoc，不要试图 patch exe 字符串**。在 `C:\tmp\larkdoc` 拉一份 `git clone --depth 1 https://github.com/chriszou/larkdoc.git`，Go 1.25 已装好。
2. 改 4 处源码：
   - `sync.go` 第 106 行：删除 `--json,` 这一项。
   - `sync.go` 第 102 行后：补 `--as user`。
   - `content.go` 第 156 行：删除 `, "--json"`，并补 `--as user`。
   - `content.go` 第 8 行：因为不再直接调 `exec.Command`，可以删掉 `os/exec` import（sync.go 仍保留 `os/exec`）。
3. 新建 `larkcli.go`，封装一个过滤 Hermes 环境变量的 helper，让所有 `lark-cli` 子进程都走它：

```go
var hermesVars = []string{"HERMES_HOME", "HERMES_QUIET", "HERMES_EXEC_ASK", "HERMES_GATEWAY_TOKEN", "HERMES_SESSION_KEY", "HERMES_GIT_BASH_PATH"}

func larkCLIEnv() []string {
	env := os.Environ()
	out := make([]string, 0, len(env))
	for _, kv := range env {
		skip := false
		for _, h := range hermesVars {
			if strings.HasPrefix(kv, h+"=") {
				skip = true
				break
			}
		}
		if !skip {
			out = append(out, kv)
		}
	}
	return out
}

func larkCLICommand(args ...string) *exec.Cmd {
	cmd := exec.Command("lark-cli", args...)
	cmd.Env = larkCLIEnv()
	return cmd
}
```

4. 把 `sync.go` 和 `content.go` 里 `exec.Command("lark-cli", ...)` 都改成 `larkCLICommand(...)`。
5. `go build -ldflags "-s -w" -o larkdoc_patched.exe .` 编译。
6. **备份原版**：`cp "C:/Users/Administrator/AppData/Local/Programs/larkdoc/larkdoc.exe" C:/tmp/larkdoc/larkdoc_original_v0.1.1.exe`。
7. **替换安装目录**：`cp C:/tmp/larkdoc/larkdoc_patched.exe "C:/Users/Administrator/AppData/Local/Programs/larkdoc/larkdoc.exe"`（用户级目录，免管理员）。
8. 源码层修复到此为止，剩下的 `search:docs:read` 是用户授权问题，不是代码问题：登录飞书开放平台，给应用 `cli_a945002535781cb0` 勾上 `search:docs:read` scope，重新走一次用户授权即可。最小权限原则，只补缺的那一个 scope，不要顺手开全部。

### 未来复用

- 任何「本机有 `lark-cli` 但要做一个新的 CLI 工具调它」的场景，都要预设这四件事：① `--json` 别瞎传（当前 lark-cli 已经不用它了）；② `--as user` 必传；③ 子进程要清 Hermes 的 5 个检测变量（`HERMES_HOME` / `HERMES_QUIET` / `HERMES_EXEC_ASK` / `HERMES_GATEWAY_TOKEN` / `HERMES_SESSION_KEY`）；④ 先确认 user scope 够用，不够只补缺的。
- 检测链路形如：`unknown flag: --json` → `bot not supported` → `hermes context detected` → `need_user_authorization ... search:docs:read`，看到这一串就要按顺序处理，不要跳。
- Go 调子进程要清环境变量时不要写死整张 `Env`，按 `os.Environ()` 过滤掉要剔除的 key，保留其他（PATH、HOME、LANG、SSL 证书等），否则 lark-cli / git / npm 一类工具直接找不到二进制或证书。
- 编译产物替换安装目录前，**必须**先备份原 exe 到 `C:/tmp/` 之外或独立目录（如 `C:/tmp/larkdoc/larkdoc_original_v0.1.1.exe`），出问题能 `unins000.exe` 走卸载流程，或者直接把备份覆盖回去。
- 重新走 `larkdoc sync --full` 时，第一次要准备好等几分钟；元数据全量翻页 + 3 并发正文拉取 + 200ms 间隔，飞书 99991400 频控会拖慢进度。
- 这次和 2026-07-30 那条「Codex 调用飞书 CLI：Hermes 误识别」是同一根因的不同切面：那条是 PowerShell 子进程移除环境变量，这条是 Go 子进程过滤环境变量。复利是同一个判断——**任何被 Codex 启动的外部命令都不应该继承 Hermes 变量**，除非它本身是 Hermes。

### 后续进展：跑通 + 关键纠错

完成上面的源码修改后，本机重新跑 `larkdoc sync --full`（清掉所有 6 个 Hermes 变量后），结果：

- 元数据同步完成：**158 篇文档** → `C:\Users\Administrator\.larkdoc\index.ndjson`
- 正文拉取：153 篇（DOCX 类型）从 1/153 跑到 49/153 后被 30s timeout 截断，但工作正常，受飞书 99991400 频控限制
- `larkdoc`（不带参数）现在可以进交互式 TUI 全文搜索

**关键纠错**：上面 2026-07-30 那条记录的「解决方案」原本写「移除 `HERMES_HOME` 和 `HERMES_GIT_BASH_PATH`」，但 **`HERMES_GIT_BASH_PATH` 根本不在 lark-cli 的 Hermes 检测列表里**——只在 Hermes 上下文中作为配套变量存在。看到源码 `internal/core/workspace.go:113-117` 才发现，**真正触发检测的 5 个变量**是 `HERMES_HOME` / `HERMES_QUIET` / `HERMES_EXEC_ASK` / `HERMES_GATEWAY_TOKEN` / `HERMES_SESSION_KEY`，只清 `HERMES_HOME` 一个大概率不够，因为 Hermes 网关通常会同时注入 `HERMES_QUIET` 和 `HERMES_GATEWAY_TOKEN`。已在 2026-07-30 那条记录里改正。

这个教训反过来也修正了本条记录的 `hermesVars` 列表和「未来复用」第 ③ 条——**应该清 5 个真正的检测变量，而不是只清 `HERMES_HOME`**。PowerShell 一行清：

```powershell
$hermesVars = @('HERMES_HOME','HERMES_QUIET','HERMES_EXEC_ASK','HERMES_GATEWAY_TOKEN','HERMES_SESSION_KEY')
foreach ($v in $hermesVars) { Remove-Item "Env:$v" -ErrorAction SilentlyContinue }
```

### 二次验证：跨 57 个版本升级仍可用

升级了 `lark-cli`：1.0.32 → 1.0.89，跨越 57 个版本。担心之前改的源码只针对老版本打补丁，升级后可能失效。结果清掉 6 个 Hermes 变量后跑 `larkdoc sync --full`，10 秒内完成：158 篇元数据同步成功，正文缓存命中无需重拉。

**判断价值**：这次验证说明上面的源码改动是「**与 lark-cli 当前行为对齐**」而非「**针对 1.0.32 版本打补丁**」——`--json` 早就被移除，所以删掉它不会因为新版本又加回来而失效；`--as user` 显式传，未来 lark-cli 默认身份再怎么改都不影响；Hermes 变量过滤的 5 个是当前检测列表里的，未来如果 lark-cli 加了第 6 个检测变量，源码改动才需要再补一次。

**可复用的判断**：写「适配外部工具」的代码时，**优先做「与当前行为对齐」而不是「针对某个版本号打补丁」**。前者随版本演化依然有效，后者一旦外部工具升级就崩。

## 2026-08-23 - Windows 用户 PATH 清理：clean-path.ps1 设计与 16 项失效项排查

### 场景

排查 larkdoc 安装时顺手诊断本机 PATH 健康度，发现用户 PATH 共 61 项里 16 项指向不存在的目录，包括截断的 `C:\Users\Administrat` 这种明显错误。

### 错误 / 弯路

1. **PowerShell `Test-Path` 对部分目录返回 false**——`C:\Windows\System32\OpenSSH`、`C:\Program Files\PowerShell\7\` 等。一开始怀疑是 PowerShell 误报，但用 cmd 的 `if exist` 验证同样返回 false，这次是真失效，不是工具问题。
2. **第一次写 clean-path.ps1 误判 `Path` 变量本身失效**——Path 变量的值就是用户 PATH 本身，里面有失效项，整串当路径传给 `Test-Path` 当然不存在。修正：`if ($k -ieq 'Path') { continue }` 跳过 PATH 自身。
3. **`echo $env:PATH` 输出是「用户 PATH + 系统 PATH」拼接（不去重）**，看起来失效项很多。要分别用 `[Environment]::GetEnvironmentVariable("Path", "User")` 和 `("Path", "Machine")` 诊断才能精确归类。
4. **`Get-Command` 在 bash → cmd 嵌套调用下 PATH 传递会截断**——明明 PATH 里有 `larkdoc.exe` 但报 NOT FOUND。bash 调 cmd 时 PATH 字符串传递问题，**不影响 WezTerm 里实际使用**。

### 根因分析

PATH 失效项的常见来源：

1. **工具残留**：卸载软件时 PATH 里的目录没清（GitHub Desktop、UniGetUI、Hermes、Claude Code 都是）
2. **版本迁移**：WezTerm 从 `terminal` 改成 `terminal-1.23.20211.0`，旧路径没删
3. **标准组件未启用**：PowerShell 7 在 PATH 里但没装；OpenSSH 在 PATH 里但 Windows 功能没启用
4. **复制粘贴累积**：装各种开发工具时自动加 PATH，删的时候不一定同步清
5. **路径被截断**：`C:\Users\Administrat`（少 `or\Administrator`）是某次复制粘贴的产物

用户 PATH 长度 2218 字符（限制 32767），**不影响性能**。失效项的真正代价是：

- 误导诊断（找不到命令时怀疑 PATH 没加，而不是怀疑路径本身失效）
- 隐藏真实安装目录（看到 `C:\Users\Administrat` 以为那是 Administrator 的目录）

### 解决方案 / 正确做法

**只动用户范围、不动系统范围**的脚本 `C:\tmp\clean-path.ps1`，四种模式：

- `-Action verify`：扫描列出失效项，不改任何东西
- `-Action backup`：单独备份当前用户 PATH 和所有用户变量到 `C:\path_backups\path_backup_<时间戳>.json`
- `-Action clean`：自动备份 + 交互确认 y/N + 清理 + 验证 15 个常用命令
- `-Action restore -BackupFile <path>`：从备份恢复

设计原则：

1. **只动 HKCU\Environment**——不需要管理员权限，最坏只影响当前用户进程
2. **不动 HKLM\SYSTEM**——系统 PATH 是 Windows 维护的，系统服务可能依赖
3. **自动备份 + 一秒恢复**——任何清理都能秒回滚
4. **交互确认**——不让脚本自作主张清，看到要清什么再按 y
5. **验证常用命令**——清理后立刻跑 15 个常用命令看是否还能用

实际跑清理：用户 PATH 61 → 45 项（去掉 16 项失效），删除失效变量 `HERMES_HOME` 和 `chocolateyinstall`，备份到 `C:\path_backups\path_backup_20260823-154806.json`，13/15 常用命令仍 OK。

### 未来复用

**脚本位置**：`C:\tmp\clean-path.ps1`
**备份位置**：`C:\path_backups\path_backup_YYYYMMDD-HHMMSS.json`
**必加参数**：`-ExecutionPolicy Bypass`（否则 PowerShell 默认策略拦）
**脚本必须纯 ASCII 注释**——PowerShell 5.x 不识别 UTF-8 无 BOM 中文，会让脚本解析失败
**非交互模式**：`echo y | powershell -File ...` pipe 输入 y 给 `Read-Host`

**什么时候跑**：

- 排查「某个命令找不到」时先 `verify` 看 PATH 是不是脏了
- 卸了一批开发工具后
- 重装系统前后做 PATH 备份 / 恢复
- 接手别人电脑时先扫一遍

**清理标准**：

- 只清 `Test-Path` 确认失效的
- 保留可能再装回来的（NVIDIA App、Claude Code 等有名字的工具）
- 永远先备份，restore 是最后保险

**判断某项该不该清的简单规则**：

- 路径被截断（少字符） → 清（明显错误）
- 旧版本目录不存在 → 清
- 工具已卸载（HKEY_CURRENT_USER\Software 里也找不到） → 清
- 拿不准 → 备份 + 留一周观察，没问题再清

**PowerShell 5.x 跟 PowerShell 7 的 PATH 行为差异**：

- 5.x：`$PROFILE` 在 `Documents\WindowsPowerShell\`，不支持 UTF-8 无 BOM 文件里的中文注释
- 7：`$PROFILE` 在 `Documents\PowerShell\`，原生 UTF-8
- 同一个 `PATH` 变量，5.x 的进程级 `Get-Command` 在 PATH 极长时会比 7 更容易截断

## 2026-08-23 - opencli doctor 误报「daemon not running」：socks5 代理协议与 undici 6.x ProxyAgent 不兼容

### 场景

装好 `@jackwener/opencli@1.8.6` 和 Chrome Browser Bridge 扩展后跑 `opencli doctor`，报 `[MISSING] Daemon: not running`、`[MISSING] Extension: not connected`、`[FAIL] Connectivity: failed`。`opencli browser <session> open <url>` 命令卡死超时。但 daemon 实际上完全健康——手动 `curl http://127.0.0.1:19825/status` 返回完整 status，PID 14924、uptime 1800 秒、`extensionConnected: true`。

### 错误 / 弯路

1. **第一反应是 opencli bug**——lark-cli 之前踩过 4 个报错链的条件反射，以为是版本兼容问题。
2. **第二反应是 daemon 真的没启动**——但端口 19825 LISTENING，手动 curl 拿到的 status 完全正常，daemon 进程也在。
3. **第三反应是 doctor 检测逻辑有 bug**——但同时直接 `import { fetchDaemonStatus }` 跑，返回 `state: 'ready'`。opencli 内部的检测函数本身能工作，问题在 doctor 走的那条路径上。
4. **跑 `OPENCLI_VERBOSE=1 node --trace-warnings ... doctor`** 才看到完整堆栈：错误来自 `requestDaemon` → `fetchWithNodeNetwork` → `undiciFetch` → `createProxyDispatcher` → `EnvHttpProxyAgent` → `new Pool(...)` 抛 `InvalidArgumentError: Invalid URL protocol`。

### 根因分析

`opencli` 启动时调用 `installNodeNetwork()` 替换全局 `fetch` 为 `fetchWithNodeNetwork`，后者用 undici 6.28 的实验性 `EnvHttpProxyAgent`。

`EnvHttpProxyAgent` 读 `http_proxy` 环境变量构造 ProxyAgent：

```js
const HTTP_PROXY = httpProxy ?? process.env.http_proxy ?? process.env.HTTP_PROXY
if (HTTP_PROXY) {
    this[kHttpProxyAgent] = new ProxyAgent({ ...agentOpts, uri: HTTP_PROXY })
}
```

当前 bash 环境 `http_proxy=socks5://127.0.0.1:7890`（从 nushell config 的 `proxy set` 函数来的，原本以为 socks5 兼容性好）。ProxyAgent 构造时用 `new Pool(uri, ...)` 创建 client，**但 undici 6.28 的 Pool 只支持 http/https 协议**——`new Pool('socks5://127.0.0.1:7890', ...)` 直接抛 `Invalid URL protocol`。

错误堆栈定位：

```
InvalidArgumentError: Invalid URL protocol: the URL must start with `http:` or `https:`.
    at parseURL (undici/lib/core/util.js:199:11)
    at parseOrigin (util.js:206:9)
    at new Pool (pool.js:70:23)
    at ProxyAgent.constructor
    at EnvHttpProxyAgent.constructor
    at createProxyDispatcher (opencli/node-network.js:122:24)
    at fetchWithNodeNetwork (opencli/node-network.js:166:21)
    at requestDaemon (opencli/daemon-transport.js:22:22)
```

**关键诊断信号**：手动 `curl http://127.0.0.1:19825/status` 走系统层代理（curl 原生支持 socks5）能成功，但 Node 进程内 fetch 不行——这指向代理**协议**而非网络问题。

**触发条件**：用户环境有 `http_proxy=socks5://...` + Node 工具用 undici 6.x 做 HTTP 客户端。

### 解决方案 / 正确做法

**关键事实**：Clash Verge、V2RayN、Surge、Quantumult X 等代理软件的 mixed port（默认 7890）**同时监听 http 和 socks5 两种协议入口**——`http://127.0.0.1:7890` 和 `socks5://127.0.0.1:7890` 连的是同一进程同一端口，只是协议不同。

最干净的修复是**把 `http_proxy` 环境变量从 socks5:// 改成 http://**：

**nushell config 改动**（`~/.config/nushell/config.nu` line 94-100）：

```nu
# 之前
def --env "proxy set" [] {
    load-env { "HTTP_PROXY": "socks5://127.0.0.1:7890", "HTTPS_PROXY": "socks5://127.0.0.1:7890" }
}

# 现在
def --env "proxy set" [] {
    load-env { "HTTP_PROXY": "http://127.0.0.1:7890", "HTTPS_PROXY": "http://127.0.0.1:7890" }
}
```

`proxy set8083` 函数同样改动。

**为什么不直接换代理软件**：很多 AI Agent 工具（puppeteer、playwright、opencli、各种 npm 包）的 HTTP 客户端都基于 undici 或类似实现，统一改环境变量协议比换软件覆盖广。

**验证**：


### 未来复用

**所有用 undici fetch 的 Node 工具**（puppeteer-core、playwright、opencli、各种 npm CLI）遇到 `Invalid URL protocol: the URL must start with 'http:' or 'https:'`：

1. **第一步**：查 `http_proxy` / `HTTP_PROXY` / `https_proxy` / `HTTPS_PROXY` 协议头
2. **第二步**：如果是非 http/https 协议（socks5、socks4），改成 `http://`（前提是代理软件同一端口监听 http 入站，主流代理软件都支持）
3. **第三步**：如果代理软件只支持 socks 没 http，升级代理软件或换 mixed port

**判断协议兼容性的快速检查**：

```bash
# curl 原生支持 socks5 和 http
curl -I -x socks5://127.0.0.1:7890 https://example.com  # 能成功
curl -I -x http://127.0.0.1:7890 https://example.com    # 也能成功

# Node 内置 fetch 用 undici，6.x 只支持 http/https 代理
node -e "fetch('https://example.com').then(r=>console.log(r.status))"  # socks5 代理下崩，http 代理正常
```

**协议兼容性速查**：

- `http_proxy=http://` → ✅ undici 正常
- `http_proxy=https://` → ✅ undici 正常（少见）
- `http_proxy=socks5://` → ❌ undici 6.x 崩，抛 `Invalid URL protocol`
- `http_proxy=socks4://` → ❌ 同上
- `HTTP_PROXY`（大写）和 `http_proxy`（小写）undici 都读，第一个非空胜出

**触发该问题的常见 Node 工具**：opencli、puppeteer-core（新版）、playwright、各种用 `fetch` 的 Node CLI（Vercel CLI、Supabase CLI、Linear CLI 等）。下次遇到同样错误模式，第一时间查代理协议。

## 2026-08-10 - Mac 代理冲突：机场客户端 SSE 流式连接阻断与 Clash 端口 7890 错配排错

### 场景
解决 macOS 客户使用 AI 工具（Codex / Work Body）时网络报错的问题。问题表现为：使用自研机场客户端时 Work Body 端口报错、切换 Clash 后 Chrome/Codex 全面断网、卸载 Clash 换回机场客户端时 Codex 在对话中频繁弹出 `stream disconnected before completion`（重新连接 2/2）报错。

### 错误 / 弯路
1. 客户之前切换到 Clash 时，由于系统代理开启但没在 Proxies 中手动选中绿色的可用节点，导致 Chrome 无法访问网页，进而对 Clash 产生不信任，卸载并换回了机场定制客户端。
2. 卸载重装 Clash 时，其 Mixed Port 会默认重置为 `7897`（或其他默认端口），而 Codex `.env` 或环境变量已写死为 `7890`，如果不手动对齐，Codex 依然会无法使用。
3. 认为机场客户端“好用且能访问网页”即可支持 AI 终端。忽略了机场自研客户端底层通常只管普通的 HTTP 网页分流，对大模型 API 常用的长连接/流式 SSE（Server-Sent Events）协议及 SSL/TLS 命令行握手支持极差，从而导致 stream disconnected 的报错。

### 根因分析
1. **Work Body 端口依赖**：Work Body 默认必须在本地 `7890` 建立通信，机场客户端不占用 `7890` 导致其直接报错。
2. **机场自研客户端协议限制**：为了节省网关连接资源，机场专属客户端会在中间掐断长时间的流式大模型 SSE 长连接。
3. **Clash 节点未选定**：Clash 默认系统代理拦截全网，如果不手动测速选好可用节点，全网流量会在本地直接断连。
4. **端口错配**：Clash 的 Mixed Port 与 Codex 中配置的环境变量（`HTTP_PROXY` 等）不一致，导致网络不通。

### 解决方案 / 正确做法
1. **统一代理工具**：彻底卸载/退出机场自研客户端，统一安装开源的 Clash (Verge / Nyanpasu)。
2. **手动对齐端口**：确保在 Clash 设置（Settings/Mixin）中将 Mixed Port 设为 `7890`，与 Codex 配置（如 `.env` 中的 `HTTP_PROXY="http://127.0.0.1:7890"`）保持一致。
3. **手动选定有效节点**：在 Clash 的代理（Proxies）页面中测速，手动选择一个绿色延迟的有效节点，解决“Chrome 网页打不开”的用户痛点。
4. **开启 TUN 模式**：通过 Clash 的 TUN 模式强制接管全网所有命令行流量（Codex），避免代理分流规则遗漏。

### 未来复用
- 遇到命令行大模型工具弹出 `stream disconnected` 或连接超时重试时，首要检查是否使用的是自研机场软件，如果是，必须劝说其换为 Clash 并选择可用节点。
- 对齐端口是客户端与代理软件协作的核心。配置好代理后，必须在终端用 `lsof -i :7890` 验证是否由代理进程监听。

### 批量生成 Obsidian 文章专栏双链（2026-07-23）

## 2026-08-03 17:46｜apply_patch 导致文件内容翻倍的根因与修复方案

**场景**：使用 pply_patch 工具对 Markdown 文件做多处替换（给18条笔记各加一行 - [ ] 自己实践），操作后文件内容变成原来的两倍——原文18条变成36条，相当于整个文件被追加了一遍。

**根本原因（已确认）**：

pply_patch 是基于"上下文匹配 + 差量替换"的工具。当补丁中的上下文行在文件中**多次出现**（本例中 - [ ] 待发布 出现了18次），工具的匹配逻辑可能将整个文件当作未匹配段，采用"追加新版本"而非"原地替换"的方式写入，导致原内容+新内容同时存在于文件中。

**触发条件**：
1. 补丁的上下文行（context lines）与文件中的多行高度重复，工具无法唯一定位
2. 补丁范围过大（跨越全文），工具回退到全文覆写模式
3. 文件较长且结构高度重复（如多条结构相同的 checklist 条目）

**正确做法——对重复结构批量修改，优先用 PowerShell 字符串替换**：

`powershell
# 读取文件（UTF-8）
 = Get-Content "路径" -Raw -Encoding UTF8

# 精确替换（用 .Replace() 或 -replace，不用 apply_patch）
 = .Replace("旧字符串", "新字符串")

# 验证替换结果
 = [regex]::Matches(, '目标模式').Count
Write-Host "替换后数量: "

# 写回（UTF-8 无 BOM）
[System.IO.File]::WriteAllText("路径", , [System.Text.UTF8Encoding]::new(False))
`

**修复方案**：
- 文件内容翻倍时，找到第二次出现的标题位置，截取前半段即可还原
- 用 $content.IndexOf("标题文本", 偏移量) 精确定位分割点

**经验总结（决策规则）**：
- ✅ pply_patch：适用于**结构唯一、上下文不重复**的精准定点修改（如改某个函数、某段唯一标题下的内容）
- ✅ PowerShell .Replace() / -replace：适用于**批量替换重复模式**（如给多条 checklist 加行）
- ❌ 不要用 pply_patch 对"多处结构相同的文本块"做批量操作——极易触发全文重写

## 2026-08-24：剪映新版草稿不能用旧模板加载失败后自动重建
