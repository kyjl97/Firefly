这两天我研究了一下 Codex 的 subagents，越看越觉得，这玩意可能是 Codex 接下来最值得折腾的能力之一。

不是因为它听起来多高级。

而是因为它解决了一个我们用 AI 写代码时特别真实的问题，**主线程太容易被搞脏了**。

一个复杂项目丢给 Codex，它要读文件、跑测试、看报错、查日志、理解架构，中间会冒出来一堆输出。有些输出有用，但大部分只是过程噪音。

主对话一旦塞满这些东西，后面就很容易跑偏。你本来只是想让它修 bug，结果聊着聊着，它开始忘记最初的约束，甚至把不该改的地方也动了。

![](https://gitee.com/da-qiang-classmate/typora/raw/master/image/codex-subagents-cover-20260623.webp)

### subagents 到底解决什么问题

我理解它的核心价值有两个。

第一个，是**减少主线程的上下文污染**。

子代理可以自己去跑命令、看日志、读文件、做探索，最后只把摘要带回来。主线程不用被一堆中间过程淹没，只需要保留需求、约束和最终判断。

第二个，是**并行省时间**。

比如一次代码审查，你可以让一个代理专看安全，一个代理专看 bug，一个代理专看测试缺口。它们各自开工，最后把结论汇总回来。

![](https://gitee.com/da-qiang-classmate/typora/raw/master/image/codex-subagents-context-pollution-20260623.webp)
### 它适合什么场景

我觉得 subagents 最适合**读多写少**的任务，比如大型代码库探索、代码审查、日志分析、文档总结、项目摸底。

但如果你让五个 Agent 同时改代码，那就有点危险了。

不是哥们，五个人同时在一个文件夹里开刀，最后谁缝合？？？

所以我自己的理解是，subagents 的正确打开方式，不是让 AI 疯狂分身写代码，而是**先让它们并行侦察**。

**先看清楚，再动手。**



### 你可以怎么叫它

下次你可以直接这样跟 Codex 说。

```text
请用子代理并行审查当前分支。
开三个子代理。
一个检查安全风险。
一个检查潜在 bug。
一个检查测试缺口。
等它们都完成后，把结果按严重程度汇总，并给出文件位置。
```

或者更简单一点。

```text
用子代理并行分析这个项目。
一个看架构，一个看测试，一个看潜在风险。
先不要改代码，等分析结果回来后再决定怎么动手。
```

这句话里最重要的是**「先不要改代码」**。因为 AI 编程真正难的地方，很多时候不是写代码，而是**别乱写代码**。

### Codex 里有哪些代理类型

Codex 默认有几个内置代理。**`default`** 是通用代理，**`worker`** 偏执行，适合实现功能、修 bug、跑验证。**`explorer`** 偏阅读，适合查代码结构、理解项目、摸清楚上下文。
![](https://gitee.com/da-qiang-classmate/typora/raw/master/image/codex-subagents-parallel-scouting-20260623.webp)
你也可以自己定义代理。

**个人全局代理**一般放在这里。

```text
C:\Users\Administrator\.codex\agents\
```

**项目级代理**通常放在项目里。

```text
.codex\agents\
```

一个自定义代理大概长这样。

```toml
name = "reviewer"
description = "专注代码正确性、安全风险和测试缺口的审查代理。"
developer_instructions = """
像代码负责人一样审查变更。
优先关注正确性、安全问题、行为回归和缺失测试。
"""
model_reasoning_effort = "high"
```

文件名不一定非要和代理名一样，但我觉得最好保持一致，少给自己挖坑。

### 我真正兴奋的点

以前我们担心的是模型能力不够，现在反而更像是，能力太多之后怎么组织。

subagents 给我的感觉，就是把 AI 从一个全能实习生，慢慢拆成一个**小团队**。有负责侦察的，有负责复核的，有负责执行的。

而你要做的，不是盯着每一行日志，而是设计好分工，告诉它们边界，等它们把干净的结论带回来。

说真的，这个方向我还挺兴奋的。

它让 Codex 不再只是一个聊天框里的编程助手，而更像一个**可以调度的工作台**。

屏幕前的你如果已经在用 Codex，可以试试下次别直接说「帮我修」。换一种说法，让它先开几个子代理并行分析，等结果回来再动手。

可能一开始会觉得慢一点，啰嗦一点。但复杂任务里，这点前置成本，往往能少走很多弯路。
