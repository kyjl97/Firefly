前几天我写过 larkdoc 的安装和排错。用完之后，我就在想：自己的博客，能不能也有一个这样的入口？

我每天都在写文章，博客里已经积累了不少关于 AI 工具、Agent、网站和工作流的内容。读者通常还是从网页进来，找到搜索框，再慢慢翻。文章本来就有标题、摘要、正文和链接，缺的只是一个更直接的入口。

这就是这个项目的起点。

![](https://gitee.com/da-qiang-classmate/typora/raw/master/image/20260825174954350.webp)


## OpenCLI 让我想起了之前装过的工具

我之前安装过 [OpenCLI](https://github.com/jackwener/opencli)，但当时只是把它装起来，并没有马上拿它做项目。它的思路很适合这个尝试：把网站上已有的内容整理成命令，让人或 AI Agent 从终端访问。

我之前那篇 OpenCLI 文章里写过“把博客封装成 CLI”的计划。这次算是把后半段补上了：从想法开始，做成一个别人可以安装的项目。

做的时候我才发现，给粉丝用和给 Agent 调用，要求并不一样。

## 我把使用路径拆成了两个入口

项目里现在有两个命令入口：

| 入口                 | 作用                    | 适合谁          |
| ------------------ | --------------------- | ------------ |
| `dq`               | 带上下键、鼠标和文章预览的可视化搜索    | 普通用户、粉丝      |
| `opencli kyjl97 ...` | 返回结构化结果，供 Agent 和脚本调用 | AI Agent、开发者 |

`dq` 是一个独立的 CLI，不依赖 OpenCLI。粉丝只需要安装 Node.js 和这个 npm 包，就可以使用。只有想让 Agent 或脚本调用结构化结果时，才需要先安装 OpenCLI，再安装插件。

这两个入口读取的是同一个博客，但解决的是两种不同的使用场景。

## 普通用户只需要输入 `dq`

安装分两步：

```powershell
npm install --global @kyjl97/kyjl97-cli
dq
```

启动之后，输入关键词，工具会搜索文章标题、摘要和正文。左边是文章列表，右边显示当前文章的预览。

- 上下键移动选择；
- 鼠标单击选择文章；
- `Enter` 或鼠标双击打开文章；
- `Esc` 或 `Ctrl+C` 退出。

![dq 终端搜索界面](/images/dq-terminal-search.webp)

我保留了选择和预览，是因为只打印一串标题还不够。看到结果后，先扫一眼摘要和正文片段，再决定要不要打开网页，查找会更快。

## 缓存解决的是一个很具体的问题

最开始的版本每次启动都重新获取文章索引。我自己测试时，反复打开几次就会遇到同一个等待：明明文章没有变化，索引还是要重新下载。

所以我给 `dq` 加了本地缓存。

第一次运行时，工具从博客公开的 RSS 地址获取文章索引，保存到本机：

```text
Windows：%LOCALAPPDATA%\dq\index.json
macOS/Linux：~/.cache/dq/index.json
```

缓存有效期是 6 小时。有效期内再次运行 `dq`，直接读取本地索引。需要立即获取最新文章时，可以执行：

```powershell
dq --refresh
```

博客发布新文章，不需要粉丝重新安装工具。缓存过期后会自动更新，也可以手动刷新。只有 CLI 本身的代码发生变化时，才需要更新 npm 包。

## 新文章怎么进入搜索结果

我的博客发布文章后，会更新公开的 RSS 索引。`dq` 下一次刷新时读取这个索引，再把文章内容放进本地搜索数据里。

我这边不需要单独维护一份 CLI 文章清单，日常动作就是正常写文章、发布文章。对使用者来说，流程是：

1. 正常写文章、发布文章；
2. 不需要手动给 CLI 添加文章；
3. 粉丝等待缓存过期，或者运行一次 `dq --refresh`；
4. 新文章就会进入搜索结果。

这里有一个需要说清楚的限制：用户本地缓存没有过期时，不会立刻看到新文章，除非手动执行 `dq --refresh`。我接受这个取舍，因为它避免了每次启动都重新下载索引。

## OpenCLI 插件给 Agent 使用

独立的 `dq` 主要给人用。OpenCLI 插件则给 Agent 和脚本提供结构化的调用入口。

安装 OpenCLI 1.8.6 或更高版本后，可以使用这些命令：

```powershell
opencli kyjl97 latest --limit 5
opencli kyjl97 search OpenCLI
opencli kyjl97 article opencli
```

它读取的是博客公开页面，只读，不需要登录，也不需要 Chrome 浏览器扩展。Agent 可以拿到文章标题、日期、分类、正文和链接，再把这些内容接到自己的工作流里。

这里也有一个边界：`opencli kyjl97 search` 目前主要匹配标题、分类和文章路径。如果要搜索正文内容，使用 `dq` 的本地索引更合适。

项目源码和完整说明已经放到 GitHub：

[https://github.com/kyjl97/dq-cli](https://github.com/kyjl97/dq-cli)

## 让别人装得上，和让代码跑起来是两回事

代码能跑之后，我还要处理安装方式、README、缓存策略、npm 包名和图片资源。这些事情不写在功能演示里，但会直接影响别人能不能用。

最开始我想把包命名为 `kyjl97-cli`，但 npm 判断它和已有的 `dts-cli` 太相似，拒绝了发布。后来改成带用户名作用域的：

```text
@kyjl97/kyjl97-cli
```

安装后的命令仍然是 `dq`，只是 npm 包名带了作用域。

README 里要说明前置条件，命令要尽量短，图片不能依赖不稳定的外链，博客更新也不能要求粉丝重新安装。代码只是其中一部分，安装和维护路径也要能走通。

## 做完之后，我对博客的看法变了

以前我更容易把网站当成内容展示页：文章写完，发布出去，事情就结束了。

做完 `dq` 之后，我发现同一批文章还可以有几种入口：网页给人阅读，`dq` 给熟悉终端的人搜索，OpenCLI 插件给 Agent 调用。内容没有增加，使用方式增加了。

回头看，这个项目就是从两个现成工具开始的：先装了一个飞书搜索工具，又想起电脑里装过 OpenCLI，最后把这个思路用到了自己的博客上。

以后再写文章时，我可能会多问一句：这段内容除了放在网页上，还能不能被工具直接找到和调用？
