# AI 长会话收尾三件套

核心思路：把**上下文、踩坑和方法**分别保存，不塞在一个地方。

> **适用前提**：超过 20 轮对话，或涉及 3 个以上文件的修改，或跨天协作，或会话即将结束时。
>
> 以下条件未满足时，根据实际情况选用其中必要的环节即可，不必全部执行。

---

## 与项目已有约定的关系

本项目 `AGENTS.md` 的**复盘与经验沉淀**章节已规定：

- 踩坑记录 → `Xenia/全局复利与踩坑日志.md`

本文的方法是 AGENTS.md 的补充执行指南，不是替代。以下三件套中的**经验记录环节**应直接写入 `Xenia/全局复利与踩坑日志.md`，而非另建独立的错题本文件。

---

## 一、HANDOFF.md —— 记录项目进度

**适用场景**：跨天任务、复杂项目、会话快结束时。

只负责记录项目当前状态，不含通用方法论。方法类内容应归入第三环节。

**内容结构**：

```
# HANDOFF — <项目/任务名称>

## 已完成
- xxx（带链接或文件路径）
- xxx

## 当前卡点
- 问题描述 + 已尝试但无效的方案

## 下一步
- xxx（标注优先级）

## 别踩的坑（本次专用）
- 仅限本项目语境下的坑，通用教训归经验记录
```

**真实示例**：

```markdown
# HANDOFF — Fuwari 博客 OGP 图片适配

## 已完成
- `src/components/PostCard.astro` 中 OGP fallback 逻辑已实现
- 测试了 3 种 fallback URL 格式，仅 `og-image-{slug}.png` 有效

## 当前卡点
- build 时动态 slug 注入失败：`Astro.url` 在构建态返回 `file://` 路径
- 尝试过 `import.meta.env` 传参，但环境变量在 build 完成后才注入

## 下一步
- [P0] 调研 `getStaticPaths` 中能否拿到输出文件名
- [P1] 备选：构建后 rename 脚本

## 别踩的坑
- 不要在 `.astro` template 中直接引用构建态 URL，要用 `Astro.url` 的运行时判断
```

**结束时使用**：

```
> 超过 20 轮或改了 3+ 个文件时强制执行。
这个会话要结束了。请写一份交接文档存到 HANDOFF.md，包括任务目标、已完成内容、当前问题、下一步计划和踩过的坑，写给一个完全没有上下文的新会话看。
```

**新会话开始时使用**：

```
请先读取 HANDOFF.md，了解项目上下文，再继续推进。
```

## 二、反思机制 —— 分析为什么出错

不要只让 AI 总结工作，还要让它分析出错原因。

### 执行前提

**先判断本次会话中是否存在纠偏事件**。如果全程没有纠正、返工或误解，跳过此环节。

判断信号：
- 你说过"不对""不是这个意思""重新来"
- AI 产出了你明确否定的内容
- 同一个问题反复修改两次以上

### 提示词（有纠偏时使用）

```
回顾这次协作，把所有被我纠正过的内容逐条列出，判断是信息不足，还是判断逻辑有问题，并告诉我下次开头增加什么指令可以避免。
用表格输出，格式如下：

| 修改内容 | 错误归因 | 下次指令建议 |
|----------|----------|--------------|
| （具体描述） | 信息不足 / 判断逻辑问题 | 开局时增加 xxx 指令 |
```

### 真实示例输出

```
| 修改内容 | 错误归因 | 下次指令建议 |
|----------|----------|--------------|
| 分类选成了 Technical，实际应该是 AIHacks | 信息不足：没有提前读取 categories 配置 | 开局先读取 src/content/config.ts，确认分类列表 |
| img URL 写了绝对路径，项目要求用相对导入 | 判断逻辑问题：默认用了常见做法而非项目约定 | 在开局指令中强调"所有图片路径参照已有文件写法" |
| 新增组件没有注册到 astro.config | 信息不足：不知道需要注册 | 开局指令追加"列出所有需要注册的文件" |
```

> 这一步的价值，是把"这次踩坑"变成"下次开局条件"。结论中的"下次指令建议"应在本会话结束前写入 HANDOFF.md 或系统记忆。

### 特殊场景处理

| 场景         | 做法                         |
| ---------- | -------------------------- |
| 本次无纠偏      | 跳过，不运行反思机制                 |
| 多次重复同一类错误  | 只列一次，归因中标注"重复出现"           |
| 错误源在用户指令模糊 | 归因为"信息不足"，在指令建议中给出更明确的表述模板 |

## 三、经验记录 —— 沉淀可复用方法

每次发现可复用的教训、审查流程、提问方式或提示词，都应该沉淀下来。

**写入位置**（统一规则）：

| 范围 | 存放位置 |
|------|----------|
| 本项目内通用 | `Xenia/全局复利与踩坑日志.md` |
| 跨项目通用 | 写入 AI 系统记忆（Memory） |

> 不要另建错题本文件。本项目已有 `Xenia/全局复利与踩坑日志.md`，所有可复用经验统一追加到该文件。如果该文件已有类似内容，先搜索确认后再决定是新增条目还是更新旧条目。

**提示词**：

```
把刚才可复用的经验录入 Xenia/全局复利与踩坑日志.md。要求：
1. 先搜索该文件中是否已有类似内容
2. 有则更新旧条目版本，不重复新建
3. 只记录可跨场景复用的方法和教训，不记录一次性细节
4. 已经写进 AGENTS.md 审查规则或提示词模板的内容也不要重复记录
```

**什么该记 vs 什么不该记**：

| 该记 | 不该记 |
|------|--------|
| "查分类前先读 config.ts" | "XX 文件的分类写错了" |
| "组件注册检查清单" | "某次 build 忘了注册" |
| "图片路径优先走相对导入" | "某张图用了绝对路径" |
| 可复用的提问/审查模板 | 某次会话的过程描述 |

## 完整执行流程

```text
开始
  │
  ├─ 是否符合触发条件？（20+轮对话 / 3+文件改动 / 跨天 / 会话结束）
  │     │
  │     ├─ 否 → 跳过，不做
  │     │
  │     ├─ 是 → 执行三件套：
  │             │
  │             1. HANDOFF.md
  │             │   └─ 记录进度、卡点、下一步
  │             │
  │             2. 反思机制（有纠偏才执行）
  │             │   └─ 分析原因 → 输出表格 → 结论写入 HANDOFF 或记忆
  │             │
  │             3. 经验记录
  │                 └─ 搜索 → 新增或更新 → 写入 Xenia/全局复利与踩坑日志.md
  │
  └─ 结束
```

### 各环节产出物

| 环节 | 产出物 | 存放路径 |
|------|--------|----------|
| HANDOFF.md | 项目进度交接文档 | 项目根目录 `HANDOFF.md` |
| 反思机制 | 纠偏分析表格（临时） | 对话中产出，结论注入 HANDOFF / Memory |
| 经验记录 | 可复用方法条目 | `Xenia/全局复利与踩坑日志.md` |
| Memory 提炼 | 跨会话持久化规则 | AI 系统记忆（通过 Memory 工具写入） |

这套流程特别适合长任务、跨天协作、Agent 工作流和复杂开发项目。建议将本文件放在项目文档入口附近，新会话开局时优先读取。
