```
所以 AI 工具安装和配置，不只是把软件装好。更重要的是帮你弄清楚三件事：这个任务是在本地跑，还是在云端跑；它能不能访问你的文件；出错以后应该看哪个日志、哪个权限、哪个账号状态。

AI 工具越强，越需要有人把复杂流程翻译成可执行步骤。否则不是模型不行，是用户卡在入口处。
```

### 2. Claude Cowork 日历 Skill
```
会用Claude Cowork的人，已经开始让它管日历了
#Claude #ClaudeCowork #AISkill #AI工作流 #小团队效率
```

```
今天 Cat Wu 分享了一个 Claude Cowork 的用法：让它管理一周日历，要求会议少于 20 小时，去掉冲突会议，参考过去几周判断哪些会该拒绝，晚餐不算进会议时长，并且让它把这个过程做成一个会持续优化的 skill，更新邀请前先问她。

这个例子非常值得拆。

它不是让 AI “帮我安排一下时间”这么简单，而是把一个人的偏好、规则、边界和确认动作都写进了流程里。

普通用户最容易犯的错，是只给 AI 一个愿望。比如“帮我整理日程”“帮我管项目”“帮我做知识库”。但真正能跑起来的 Agent，需要的是规则：什么叫太忙，哪些会议优先，哪些事情必须问我，哪些可以自动处理。

这也是 Skill 定制真正有价值的地方。它不是一个炫技 prompt，而是把你重复解释的工作规则固化下来。

你可以把它用在日历，也可以用在 Obsidian 笔记整理、客户咨询分流、短视频选题筛选、网站内容更新、每周复盘生成。

关键不是让 AI 一次性变聪明，而是让它每次都按你的工作习惯执行。

如果一个任务你已经对助理解释过三遍，它很可能就适合做成一个 Skill。
```

```
今天 Thariq 提到，如果你遇到了某个 Claude Code 问题，可以先重启，修复正在传播。他还说正在写一篇复盘，讲他们学到了什么，以及这些经验怎么应用到 skills 和 system prompts 里。

这类信息对普通用户很有价值，因为很多人用 AI 编程工具出问题时，第一反应是怀疑自己是不是哪里操作错了。

但现实是，Claude Code、Codex、各种 Agent 工具都在高速迭代。一个报错可能来自你的配置，也可能来自工具端更新，也可能是插件、权限、模型、上下文策略临时变化。

所以排查时不要一上来就乱改。更稳的顺序是：先确认是否是已知问题；再重启和更新；然后看本地配置、项目规则、权限模式、环境变量；最后再改 prompt 或脚本。

这里面 system prompt 和 skill 很关键。它们决定了 AI 工具看到任务后怎么理解边界、怎么检查文件、什么时候问你、什么时候继续执行。

如果你的 Claude Code 经常跑偏，不一定是模型不懂你，也可能是你的项目规则、技能说明和工作流入口没有写清楚。

真正的排错不是把错误按掉，而是把“下次怎么避免”沉淀到配置和 Skill 里。
```

```
AI越便宜，小团队越需要算清楚怎么用
#AI模型 #Token成本 #AIGateway #API配置 #AI顾问
```

```
今天 Aaron Levie 讲了一个判断：很多人以为 AI 成本下降以后，大家在 AI 上的花费会下降，但通常相反。因为 token 变便宜之后，人们会把 AI 用到更多任务里，比如写更多代码、做更多代码审查、跑更大的数据集、让 agent 做更多事。

这句话对小团队特别现实。

现在很多人选 AI 工具，只看单价：哪个会员便宜，哪个 API 便宜，哪个模型每百万 token 便宜。但真正落地后，成本不只看单次价格，而要看你把它接进了多少流程。

如果只是偶尔问问题，一个账号就够了。如果你开始让 AI 自动整理资料、生成文章、跑网站构建、读 Obsidian、做代码 review、批量处理客户咨询，那 token 消耗会很快变成运营成本。

所以模型 API 配置不能只问“能不能调通”。还要提前设计：哪些任务用强模型，哪些任务用便宜模型；哪些步骤必须人工确认；失败重试会不会无限烧钱；日志和账单在哪里看。

这也是 AI Gateway、模型路由、成本监控会越来越重要的原因。

AI 省时间是真的，但如果没有工作流设计，它也可能悄悄把预算吃掉。
```

```
很多 demo 看起来很厉害，做个页面、改个按钮、生成一段代码都很顺。但一到真实环境，问题就变了：依赖装不上、端口冲突、账号权限不对、Windows 路径编码出错、API key 放错位置、部署失败、日志看不懂。

open weights、商业模型、API Gateway、Claude、Codex、Gemini 都可以成为工具箱的一部分，但前提是你知道每个工具适合什么任务。

真实技术服务的价值，不是让 AI 做一个好看的 demo，而是把出问题的那一步修到能交付。
```

### 6. Markdown 和 GSkills
```
为什么我一直建议你把资料先整理成Markdown
#Markdown #Obsidian #GSkills #知识库 #AI写作系统
```

```
今天 Garry Tan 说了一句很适合知识工作者的话：Markdown 文件很通用，会活很久。在 AI 技术栈变化这么快的时候，它反而是一种很好的数据格式。他还顺手提到了 GSkills。

这件事和 Obsidian 用户特别相关。

很多人一开始做 AI 知识库，会纠结要不要上数据库、向量库、复杂 RAG、自动同步平台。不是说这些没用，而是如果你的基础资料都还散在微信、飞书、网页收藏、Word、截图里，先上复杂系统只会更乱。

Markdown 的好处是简单、可读、可迁移。今天你可以用 Obsidian 管，明天可以给 Claude Code 读，后天可以拿去生成网站，也可以作为 Skill 的参考材料。

AI 工作流最怕资料被锁死在某个工具里。你换模型、换 Agent、换编辑器时，内容还应该能带走。

所以我更建议普通创作者先把核心资产整理成 Markdown：文章、口播稿、客户问题、项目记录、踩坑日志、服务说明、常见报错。

等这些资料有结构了，再考虑自动标签、检索、网站发布、Agent 调用。

AI 时代真正值钱的不是你今天用了哪个新工具，而是你的个人语料能不能长期被不同工具使用。
```

### 7. 一次性软件
```
以后很多小工具，不需要永远维护
#VibeCoding #个人网站 #AI工具 #工作流自动化 #Codex
```

```
今天 Zara Zhang 提到一个很实用的观点：我们要习惯代码和软件可以是一次性的。比如为了调设计做一个临时 playground，为了理解代码生成一个 HTML 页面，为了检查某个问题临时拉一个 dashboard，用完就丢。

这个方向对个人创作者和小团队很重要。

以前一听到“做软件”，大家默认就是要立项、设计、开发、部署、维护。但 AI 编程工具把很多一次性需求变得很轻。

比如你想看 Obsidian 里某类笔记的数量，可以临时生成一个统计页。你想比较 20 个选题，可以做一个小看板。你想给客户解释网站结构，可以生成一个 HTML 示意页。你想检查一批 Markdown 文件的标题和标签，也可以写一个一次性脚本。

这些东西不一定都要做成正式产品。只要能帮你完成判断、减少重复操作、把问题看清楚，就已经有价值。

但这里有个前提：一次性不等于随便。临时工具也要知道读哪些文件、输出到哪里、能不能覆盖、怎么验证结果。

Codex、Claude Code 这类工具最适合处理这种“小而具体”的任务。不要一上来就想做大系统，先让 AI 帮你做一个当天就能用的小工具。
```

### 8. 70% Copy Edit 自动化
```
AI写作自动化，不是让它替你想，而是替你修
#AI写作 #内容工作流 #Obsidian #自动化 #个人IP
```

```
今天 Dan Shipper 说，他们内部过去一周已经能自动完成大约 70% 以前需要人工做的 copy edits，而且这是他尝试多年后第一次真正越过这个门槛。

这条对内容创作者非常关键。

很多人用 AI 写作，目标一开始就错了：总想让 AI 从零写出一篇像自己的文章。结果出来的东西很完整，但没有你的判断、你的经历、你的语气。

更可落地的方式，是让 AI 先做编辑，而不是做作者。

你先把真实想法写出来，哪怕很乱。然后让 AI 帮你做结构调整、删重复、补过渡、统一标题、检查口播是否顺口、把硬广告改成自然承接、把专业词改成人话。

如果你有 Obsidian 里的历史文章、短视频脚本、服务复盘和客户问答，AI 的编辑质量会更稳定。因为它不是凭空猜你是谁，而是在你的材料里找表达习惯。

内容自动化真正值得做的，不是每天批量生产一堆空稿，而是把你已经会说的话，变成更稳定、更容易发布的成品。

这就是为什么写作系统、个人语料库和自动审校流程，会比单个爆款 prompt 更重要。
```
