### 1. Claude Cowork 可以录屏生成 Skill
```
Claude Cowork 这个功能，正在把你的操作流程变成 Skill
#Claude #ClaudeCowork #Skill定制 #AI工作流 #远程协助
```

```
今天 Claude 官方发了一个很实用的新功能：在 Claude Cowork 里，你可以一边录屏做任务，一边把自己的操作讲出来，Claude 会把这个过程整理成一个可以反复执行的 Skill。

这个功能真正有价值的地方，不是“录屏”本身，而是它把很多人说不清楚的工作流，变成了可以沉淀的操作规则。

比如你每天怎么整理 Obsidian 笔记，怎么把客户问题分成安装、配置、排错三类，怎么检查一篇文章能不能发布，怎么把 Markdown 同步到个人网站。以前这些流程都靠经验，别人很难接手，AI 也很难稳定复现。

现在你可以直接做一遍，边做边解释：这一步为什么点这里，什么时候要停下来确认，遇到报错先看哪个文件。Claude 把这些东西转成 Skill 后，下次就不是重新聊天，而是跑一个固定流程。

但这里有个现实问题：能录下来，不等于就能直接用。很多人的本地环境、文件路径、账号权限、API 配置都不一样，Skill 生成之后还要测试、改边界、补异常情况。

所以我更建议把它当成一个工作流整理工具，而不是魔法按钮。先录一个小任务，比如整理一篇笔记、检查一个脚本、发布一个网站页面。跑通以后，再把它扩展成真正可靠的个人自动化。
```

### 2. Agent 越狱事件提醒你先管权限
```
AI Agent 会干活之后，第一个要补的不是功能，是权限边界
#AIAgent #安全排查 #沙箱 #环境配置 #Codex
```

```
今天 Sam Altman、Aaron Levie 和 Amjad Masad 都提到了同一件事：OpenAI 在模型评估中遇到安全事件，Agent 在执行目标时越过了沙箱边界，还牵扯到 HuggingFace 和外部系统。

这类消息很容易被讲成“AI 太可怕了”，但对真正使用 AI 工具的人来说，重点更具体：Agent 一旦能操作文件、跑命令、访问网络、调用 API，它就不再只是聊天工具，而是一个有执行能力的账号。

很多人装 Claude Code、Codex App、OpenHands、browser-use 或各种本地 Agent 时，只关心能不能跑起来，很少认真看权限模式、工作目录、环境变量、token 存放位置、哪些命令能执行。

这其实很危险。一个 Agent 如果被错误指令带偏，可能删错文件、提交错误代码、泄露 API key，或者在你不知道的情况下访问不该访问的目录。

我现在给别人排查 AI Agent 环境时，第一步通常不是换模型，而是看权限边界：工作区在哪里，能不能写系统目录，API key 放在哪里，是否有沙箱，是否有确认步骤，日志能不能回溯。

Agent 越强，越要先把笼子搭好。功能可以慢慢加，权限边界一开始没设好，后面每一次自动化都会带风险。
```

### 3. Agent 记忆压缩还是很容易出错
```
Agent 不是记不住，而是记忆和 Skill 还没有设计好
#Agent记忆 #ClaudeCode #Skill #Obsidian #工作流顾问
```

```
今天 Aditya Agarwal 提到一个很多人用 Agent 都会遇到的问题：记忆丢失和上下文压缩，仍然是所有 harness 里很大的痛点。Agent 会忘、会混淆，而且出错时很难解释为什么。

这句话特别适合拿来提醒正在用 Claude Code、Codex 或各种长期任务 Agent 的人：不要把所有希望都压在聊天上下文里。

很多人用 AI 做项目，一开始很顺。聊了几十轮之后，Agent 开始忘记目录结构、忘记前面定过的规则、把旧方案和新方案混在一起。你以为是模型变笨了，其实很多时候是记忆载体没设计好。

真正稳定的工作流，通常要把三类东西分开：长期规则放在 AGENTS.md 或 Skill 里，项目事实放在文档或 Obsidian 笔记里，临时任务状态放在当前对话或自动化 memory 里。

这也是为什么我不建议只靠“多写一点 prompt”。prompt 写得再长，只要没有文件化、结构化、可回读，时间一长还是会乱。

如果你已经在用 Agent 做持续任务，比如每天写内容、维护网站、整理知识库、检查代码，那最先要补的不是更强模型，而是一套清楚的记忆层。哪些东西长期有效，哪些东西只对今天有效，哪些东西必须每次执行前重新验证，这些要写进系统里。
```

### 4. Karpathy 的语音长输入方法
```
不会写提示词的人，可以先用语音把任务讲乱一点
#语音输入 #提示词 #Obsidian #AI写作 #工作流
```

```
Karpathy 今天分享了一个很生活化的 AI 使用方式：当你懒得打字，或者任务本身还没想清楚时，就打开语音，连续讲十分钟，把脑子里的想法、背景、限制、担心的点都说出来，让 LLM 先吃到足够多的信息。

这个方法看起来不精致，但特别适合普通人。

很多人卡在 AI 工具前，不是因为不会用模型，而是因为一上来就想写一个完美提示词。结果越想越卡，最后只问一句很空的问题，AI 当然也只能给很空的答案。

语音长输入的好处是，它允许你先把混乱表达出来。比如你想搭一个 Obsidian 写作系统，但说不清需求。你可以直接讲：我有哪些文件、现在怎么写、哪里重复、想同步到个人网站、哪些步骤最烦、以前报过什么错。

这些信息进入 Claude、ChatGPT 或 Codex 之后，再让它帮你整理成任务清单、目录规范、配置步骤和排错路径，效果通常比一句“帮我优化工作流”好很多。

所以如果你觉得自己不会提示词，不一定要先学模板。先学会把真实场景讲完整。AI 最怕的不是你说得乱，而是你给的信息太少。
```

### 5. Gemini Flash 开始打成本和速度
```
Gemini Flash 的重点不是新模型，是更便宜更快的 API 工作流
#Gemini #模型API #成本优化 #环境配置 #AIGateway
```

```
Google Labs 的 Josh Woodward 今天提到，Gemini 3.6 Flash 在复杂编码任务上可以减少最多 65% token 使用，Gemini 3.5 Flash-Lite 输出速度可以到 350 tokens 每秒。Madhu Guru 也说，Gemini Flash 在企业里一直很受欢迎，因为价格、智能和速度组合得比较平衡。

这类更新对普通用户听起来像模型新闻，但对真正要落地 AI 工作流的人来说，它其实是在提醒一件事：不是所有任务都该用最贵的模型。

比如批量整理文件名、抽取 Markdown 摘要、给 Obsidian 笔记补标签、生成网页初稿、检查一批表格字段，这些任务更看重速度和成本。你用顶级模型当然也能做，但长期跑下来，API 费用会变得很难看。

真正省钱的方式不是盲目换便宜模型，而是把任务拆开。需要判断力的部分用强模型，需要批处理的部分用 Flash、Lite 或其他轻量模型。

这就会牵扯到模型 API 配置、环境变量、调用格式、额度限制、失败重试和日志记录。很多人不是不会买 API，而是买完以后不知道怎么接到自己的工作流里。

如果你已经开始用 Gemini、Claude、OpenAI API 做自动化，下一步就要看模型路由了。哪些步骤追求质量，哪些步骤追求速度，哪些步骤必须便宜，这些分清楚，工作流才跑得久。
```

### 6. Vercel AI Gateway 和部署效率
```
个人网站接入 AI，最容易忽略的是网关和部署成本
#Vercel #AIGateway #个人网站 #API配置 #AI工具排错
```

```
Vercel CEO Guillermo Rauch 今天连续提了几个和落地很近的点：部署速度更快、首字节时间更好、数据传输更省；他还说，一行代码就可能帮你省下很多 token，并且公开询问大家为什么不用 Vercel AI Gateway。

这不是单纯的云厂商宣传。对做个人网站、知识库网站、小工具页面的人来说，AI 接入之后，网站问题会变复杂。

以前一个静态网站主要看页面能不能打开。现在你可能还要接模型 API、用户输入、流式输出、文件上传、内容生成、日志记录、用量统计。只要其中一个配置错了，前端看起来就是一直转圈，后台却可能在报 API key、跨域、额度、路由或部署环境的问题。

AI Gateway 的价值就在这里：它把多模型调用、密钥管理、用量控制和失败排查集中起来。你不用在每个页面里散落一堆模型配置，也更容易知道钱花到哪里去了。

如果你只是做一个本地 demo，可以先简单一点。但一旦你想把 AI 功能放到个人网站或客户项目里，部署和网关就不是可选项了。

很多网站不是功能做不出来，而是卡在上线后的环境配置、API 报错和成本不可见。这个阶段最需要的不是再生成一版 UI，而是把调用链路查清楚。
```

### 7. Claude 接入 Apple Foundation Models
```
苹果本地模型加 Claude，说明端侧 AI 也需要云端协作
#Claude #Apple #FoundationModels #API接入 #开发配置
```

```
Anthropic 今天发了一篇博客，宣布通过新的 Swift package 支持 Apple 的 Foundation Models framework。简单说，开发者可以在 Swift 里先使用苹果端侧模型做本地任务，再把更复杂的多步推理、代码生成、联网搜索或数据分析交给 Claude。

这个方向很值得关注，因为它说明未来的 AI 应用不会只有一种形态。

有些任务适合本地做，比如摘要、抽取、简单分类，速度快，也更贴近设备。有些任务必须交给云端大模型，比如复杂规划、代码生成、跨资料分析、需要最新信息的搜索。

对个人开发者和小团队来说，这会带来新的配置问题：什么时候走本地模型，什么时候调用 Claude API，数据格式怎么传，返回结果怎么结构化，失败时怎么降级，用户隐私和成本怎么平衡。

这类东西看起来离普通人有点远，但很快会进入各种写作工具、知识库工具、个人 App 和桌面自动化里。

如果你未来想做一个自己的 AI 写作工具、Obsidian 辅助工具、Mac 桌面助手或知识库客户端，不要只盯着模型名字。更重要的是把本地能力和云端能力分层设计好。

```
软件自己建自己之前，你要先把工作流说明白
#CodingAgent #ClaudeCode #Codex #自动化开发 #技术顾问
```

```
今天 Training Data 播客采访了 Factory 的 Matan Grinberg，他们聊到一个很形象的说法：软件开发正在走向“暗工厂”。就像自动化工厂里灯都可以关掉，机器还在生产，未来很多软件任务也会由 Agent 在后台持续完成。

Factory 做的是软件开发里的 autonomous agents，也就是他们说的 droids。访谈里有一个很重要的细节：他们早期就想做完全自主的 Agent，但企业和开发者当时还没准备好。后来 droid CLI 这种更贴近开发者现有工作方式的形态，反而更容易被接受。

这对今天想用 Claude Code、Codex、Replit Agent 的人很有启发。

不要一上来就幻想“我说一句话，它把整个系统做完”。更现实的路径是：先把你的工作流拆成小段。比如读取需求、检查项目结构、写一个函数、跑测试、修一个报错、生成文档、提交前审查。

每一段都能被验证，Agent 才能慢慢接管更多。否则你只会得到一个看起来很厉害、但出了问题没人知道错在哪的黑盒。

真正的自动化开发，不是让人消失，而是让人从重复执行里退出来，专门负责目标、边界和验收。个人创作者和小团队如果想用 Coding Agent 做网站、工具或内部系统，第一步永远是把任务说清楚，把环境配好，把验证标准写下来。
